# 슬로그 코드 실행 기능: grill-with-docs

진행 방식: 민수가 직접 interviewing과 domain-modeling을 수행한다. 기능 구현은 요구사항 검증과 최종 공통 이해 확인 이후에 시작한다.

## 확인된 요구

- 별도 서비스 화면으로 이동시키는 기능이 아니라 슬로그 글의 코드 블록에서 시작한다.
- 재생 버튼 위치는 코드 블록 오른쪽 위다.
- 작성자가 실행용으로 지정한 코드 블록에만 재생 버튼을 표시한다. 일반 코드 블록에는 자동으로 표시하지 않는다.
- 재생은 새 창 대신 같은 페이지의 레이어 팝업을 연다.
- 설치 과정 없이 브라우저에서 실행 환경을 사용할 수 있어야 한다.
- 팝업에서 변경한 코드를 원문 글에 저장하는 기능은 제공하지 않는다.
- 팝업 안에서 실험 코드를 임시로 수정하고 다시 실행할 수 있다. Q2 사용자 동의로 확정했다.
- Q3 확정. 슬로그의 하나의 기능으로 제공하며, 컴파일·실행·추적을 모두 브라우저 안에서 처리한다. 서버나 외부 서비스에 코드를 보내 실행하지 않는다. WebAssembly와 Web Worker를 최대한 활용하고, 이 조건에서 지원할 수 없는 언어는 제외한다. Rust·Go도 예외가 아니다.
- Q4 확정. 첫 버전은 한 파일로 실행 가능한 예제를 지원한다. 웹 예제는 HTML 한 파일에 CSS와 JavaScript를 포함할 수 있다. 여러 파일 프로젝트는 첫 버전 범위에서 제외한다.
- Q5 확정. 팝업을 닫고 다시 열면 글 원문의 코드와 초기 상태로 시작한다. 실험 상태를 보존하지 않는다.
- 스타터킷을 제공한다. React 실행 준비와 JSX 변환 등 반복 설정을 작성자가 매번 작성하지 않도록 미리 정해진 실행 환경을 선택한다. 사용자는 fenced code block의 이름으로 스타터킷을 고르는 방식을 예시로 들었으며 정확한 식별자 문법은 아직 확정하지 않았다.
- Q6 확정. 스타터킷에는 버전 1·2·3처럼 번호가 있고, 기존 버전 자체를 수정하는 것과 새 버전을 만드는 것을 모두 허용한다. 공개 버전을 immutable하게 고정하지 않는다. 글의 버전 참조 방식은 다음 질문에서 구체화한다.
- Q7 확정. React 기본 킷과 React+Tailwind 킷을 별도로 제공한다.
- Q6-1 확정. 글은 선택한 스타터킷 버전을 계속 참조한다. 그 버전의 내용 수정은 반영하고, 새 번호의 버전을 추가해도 자동으로 참조를 전환하지 않는다.
- Q8 확정. 스타터킷은 개발자인 사용자가 개발 코드로만 추가·수정·버전 관리한다. 사이트의 관리자용 CRUD 화면이나 일반 작성자의 킷 등록 기능은 만들지 않는다. 글 작성자는 제공된 킷과 버전을 선택한다.
- Q9 확정. 코드 펜스 이름에 킷 이름과 버전을 적는다. 추천 예시 `react-starter-1`, `react-tailwind-starter-1`을 채택한다.
- Q10 확정. 팝업을 열면 원문 코드를 한 번 실행한다. 수정 후에는 실행 버튼으로 다시 실행하고, 타이핑마다 자동 실행하지 않는다.
- Q12 최종 수정. 사용자가 실시간 입력 우선안을 철회했다. 첫 버전은 실행 전 선입력만 지원한다. 실시간 입력은 우선 시도하지 않으며 후속 검토로 남긴다. 이는 프로그램 표준 입력에 관한 범위 결정으로, 실시간 DOM 관찰 요구와는 구분한다.
- Q13 확정. 코드와 실행 상태는 다시 열 때 원문과 초기 상태로 돌아간다. 패널 배치·크기·열림 상태 같은 화면 설정만 같은 브라우저에 기억한다.
- 사용자는 최종 합의안에 동의하면서 웹 렌더링 화면의 기본 텍스트 글꼴을 Pretendard로 지정했다. 이 설정은 콘솔이나 코드 편집기 글꼴을 바꾸라는 요구가 아니다. 해당 조건을 포함해 공통 이해 확인을 마쳤다.
- 실험 화면은 코드 편집기, 콘솔, 입력과 여러 독립적인 결과·시각화 패널을 제공한다. 패널은 개별적으로 열고 닫을 수 있고, CodePen처럼 레이아웃을 선택할 수 있으며, 패널 사이 핸들로 크기를 조절할 수 있어야 한다. 언어별 실제 지원 범위와 범용 UI 제공 여부는 구분해 검토한다.
- 렌더링 화면, 실시간 DOM 비주얼라이저, React VDOM 비주얼라이저, 메모리 비주얼라이저는 각각 별도의 패널이다. 하나의 '시각화/결과' 패널로 합치지 않는다. 모든 패널을 동시에 사용하도록 강제하지 않는다. C 예제는 코드 편집기와 메모리·콘솔·입력으로 구성할 수 있어야 한다.
- 웹 실험 환경과 Java·C·C++ 실행 시각화를 원하며 JavaScript·TypeScript·Rust·Go까지 가능한 범위를 검토한다.
- 셋업 스킬 재실행은 완료했다. 기존 용어는 GLOSSARY.md로 보존했고 최신 도메인 소비 템플릿을 적용했다.

## 설계 트리

1. 실행 진입점
   - Q1 확정. 작성자가 실행용으로 지정한 블록에만 재생 버튼을 표시한다.
   - 그다음: 실행용 작성 문법과 여러 파일/웹 패널을 한 실험으로 묶는 방법.
2. 실험 범위
   - 팝업 안에서 임시 코드 수정과 표준 입력을 허용할지.
   - 닫고 다시 열 때 원문으로 초기화할지, 세션 중 임시 상태를 유지할지.
3. 언어와 결과
   - 최초 제공 범위와 후속 지원 우선순위.
   - 단순 실행 결과와 단계별 메모리 시각화의 구분.
4. 실행 제공 방식
   - 제공자별 실제 지원 범위, 라이선스, 임베딩, 초기 소스 전달, 실행 제한은 코드·공식 문서로 직접 조사한다.
   - 조사 후 외부 실행 서비스 사용 여부와 서비스 의존성 허용 범위를 결정한다.
5. 문서와 팝업 수명
   - 글 내용 갱신·페이지 이동·팝업 닫기·여러 실행 블록 간 전환의 동작.
   - 키보드·오류·시간 제한·중지 동작.

## 현재 질문

Q1은 사용자 동의로 확정했다. 사용자는 질문 집합을 먼저 화면에 출력한 뒤 그 집합에 대해 묻도록 요청했다. 이후 라운드는 그 방식으로 진행한다.

### 다음 라운드의 질문 집합

- Q2 확정. 팝업 안에서 임시 코드 수정과 재실행을 허용하고 글 원문은 바꾸지 않는다.
- Q3 확정. 서버 실행은 허용하지 않는다. 모든 컴파일·실행·추적을 브라우저에서 처리하고 가능한 언어만 지원한다.
- Q4 확정. 첫 버전은 단일 파일 예제만 지원한다. 웹 예제는 HTML 안에 CSS와 JavaScript를 포함할 수 있다.
- Q5 확정. 다시 열면 원문 코드와 초기 상태로 시작한다.

Q2~Q5는 확정했다. 질문 집합을 먼저 출력한 뒤 한 항목씩 묻고 답변을 기록한다.

### 스타터킷 질문 집합

- Q6 확정. 기존 스타터킷 버전 수정과 새 버전 추가를 모두 허용한다. 버전을 immutable하게 고정하는 첫 제안은 채택하지 않았다.
- Q6-1 확정. 선택 버전 수정은 반영하며 새 버전으로 자동 전환하지 않는다.
- Q7 확정. React 기본 킷과 React+Tailwind 킷을 구분한다. 정확한 작성 문법과 진입 코드 형태는 뒤에서 검토한다.

Q6, Q6-1, Q7 모두 사용자 동의로 확정됐다. 스타터킷 실행도 Q3의 브라우저 전용 경계를 따른다.

### 관리·작성·시작 동작 질문 집합

- Q8 확정. 개발자인 사용자만 개발 코드로 킷을 등록·수정한다. 관리자 CRUD 화면은 만들지 않는다.
- Q9 확정. `react-starter-1`, `react-tailwind-starter-1`처럼 킷 이름과 버전을 코드 펜스에 적는다.
- Q10 확정. 처음 열 때 실행하고, 이후 수정은 수동 재실행한다.

Q8~Q10은 확정했다. Q8은 관리자 화면이라는 첫 제안 대신 개발 코드 등록으로 정했다. 새로운 질문은 근거와 선택지를 준비해 먼저 출력한 뒤 한 항목씩 묻는다.

### 패널·입력 질문 집합

- Q11 수정. 사용자가 결과와 각 비주얼라이저는 별도 패널이라고 명확히 했다. 결과/시각화를 합친 기존 기본 배치안은 채택하지 않는다. 실제 렌더링, DOM, React VDOM, 메모리를 분리하고 언어·킷에 맞는 패널 조합을 사용한다. 정확한 기본 배치는 이후 실제 화면으로 확인한다.
- Q12 최종 확정. 선입력만 지원한다. 실시간 입력은 우선 시도하지 않고 나중에 검토한다. 이전 실시간 입력 우선 결정은 철회됐다.
- Q13 확정. 화면 설정만 브라우저에 보존하며 코드와 실행 상태는 보존하지 않는다.

Q11의 패널 분리 원칙과 Q12·Q13은 확정됐다. 정확한 기본 배치는 실제 화면 검토로 다듬고, 기본 배치의 기존 합친 시각화 패널 가정은 사용하지 않는다. 현재까지 합의한 요구를 종합해 사용자에게 공통 이해의 최종 확인을 받은 뒤 기술 검증과 설계를 진행한다.

## 조사 사실과 한계

- 기존 Viewer의 fenced-code renderer를 확장할 연결 지점이 있다.
- 기존 Java 시각화 프로젝트는 브라우저 컴파일·실행·추적을 제공하지만 현재 README는 비공개 기술평가와 공개 배포 전 의존성 확인을 명시한다. 공개 서비스에 바로 복사해도 된다고 단정하지 않는다.
- 모든 언어가 같은 실행·메모리 시각화를 제공한다고 가정하지 않는다.
- 원격 실행 API나 서버 기반 시각화 임베드는 Q3 결정으로 후보에서 제외한다. 정적 런타임 자산을 내려받는 것과 코드를 서버에서 실행하는 것은 구분한다.
- 임시 코드 수정과 재실행 허용은 Q2에서 사용자 요구로 확정됐다.

## 문서 반영

용어가 합의되는 시점에 GLOSSARY.md에 정의만 기록한다. 구현 방식은 이 인터뷰 기록과 필요할 때의 스펙에 둔다. ADR은 되돌리기 어렵고 실제 대안 간 선택이 필요한 결정이 생길 때만 작성한다.
